## 1. 交付重点与范围

下一阶段主线是：版本化业务资源与模型配置 → 独立质量评测 → 单个真实远程后端 → 有限改进实验 → 当前版本的演示与报告。

| 范围 | 本阶段安排 | 完成后可证明的能力 |
|---|---|---|
| rag.index、agent.extract 独立评测 | 必做，先用免费本地模型建立基线 | 数据与标签设计、指标口径、错误分析 |
| 一个供应商的同步 embedding / 结构化抽取 | 主线，供应商及费用确认后执行真实验收 | 模型适配、调用治理、业务版本与兼容性 |
| 有限改进实验 | 必做，可先在本地完成 | 根据证据选择分块或提示词方案，解释效果与成本 |
| 当前版本性能、自然租约恢复与演示 | 必做；W4 调查限定投入 | 可观测排障、可靠性语义、可信测量 |
| 最小备份恢复演练 | 可选尾项，独立 PR | 数据恢复与部署操作能力 |
| AT-25、完整生产 HA / PITR、长周期观测留存 | 后置 | 继续单列边界，不纳入本阶段完成声明 |

沿用两个任务类型，保持 PostgreSQL 唯一任务事实源、at-least-once、原子 Claim、lease/fencing、终态不可变与租户隔离。保留 Go Runtime 为唯一租约持有者，Python 只负责 SDK 提交与评测汇总。PageWise 不回归。首轮不引入通用 Agent 框架、动态工具执行、工作流引擎、外部向量库或新的调度系统。

## 3. S0：先冻结业务契约

交付一个 PRD v0.7 与一项新的模型适配 / 评测版本 ADR 草案（下一编号执行时核对，当前为 0013）。按 [ADR 流程](../adr/README.md) 评审、合并后接受；不静默改写 ADR-0011/0012。

建议一次解决以下相互依赖的边界：

1. **版本化资源**：保留 v1 的固定样例。v2 只引用部署时预注册的 dataset / document / schema / execution_profile ID，不接受任意路径、URL、模型名、提示词文本、租户或工具指令。第一轮资源继续随业务适配器打包；原文只在业务资源及受控产物中保存。
2. **不可变执行配置**：profile 包含 provider、地域、精确模型标识、文档 / 查询编码方式、向量维度、分块、提示词、Schema 与调用上限。任务提交时携带注册的 profile 版本；重投和人工 retry 不改用部署时新的默认值。同一 profile ID 不得被原地改义。消费同一queue的Worker必须具备同一profile目录；不同模型能力用既有queue/Worker声明隔离，避免合法任务被不具备该profile的Worker领取后失败。
3. **业务指纹与兼容性**：输入内容 hash、profile hash、算法、模型、提示词、Schema 共同构成内容指纹。同业务键异配置明确冲突；同 job 重投及人工 retry 保留业务键。不同实验或独立复测使用新键。v1 本地索引继续可查，旧 profile 不可用时明确拒绝，不能静默换 embedding。
4. **索引身份**：不只比较维度；provider/model revision、维度、编码模式与预处理共同定义向量空间。查询按照产物绑定的 profile 选择 embedder。供应商没有权重摘要时记录其实际可提供的模型身份与时间，不伪造本地 digest 等级的保证。
5. **有界输出**：v1 字段语义不变；v2 第一轮继续对缺关键字段、冲突或非目标文档明确失败并不发布错误产物。若未来需要 null / needs_review，另增 Schema 版本。模型输出截断计入明确失败或现有一次修正机会。
6. **计量与预算**：扩展业务模型结果的有界元数据，计入失败 / 超时 / 查询调用；公开错误、产物结构或指标变化均写明兼容性。验收批次由服务端登记并绑定tenant，创建/增加额度属于管理员配置。提交、人工retry和产物查询必须解析到授权批次；缺失或伪造批次ID不能绕过预留、创建新额度或消耗其他租户额度。新增持久表只用 versioned migration，保持在业务层。

## 4. 评测设计

### 4.1 数据与切分

建议先做 10 条检索问题和 10 份抽取文档的小批试运行，核对标注、输入长度、调用次数与报告，再冻结正式 manifest。

| 任务 | 首轮建议规模 | 切分及覆盖 |
|---|---|---|
| RAG | 12～20 篇短文档；单索引总输入≤64 KiB、分块≤64；60 条问题 | 开发 40 / 保留测试 20；建议可回答 48、无相关内容 12，分别按 32+8 / 16+4 分配；查询改写族与主题分组切分 |
| 抽取 | 60 份人工核对的合成采购文档，每份≤64 KiB；模型上下文预算可以进一步收紧 | 开发 40 / 保留测试 20；48 份有效、12 份缺字段 / 矛盾 / 非目标文档；按至少六类表达或模板族分组切分 |

这些数量是控制工程成本的起点，不是统计学充分性承诺。数据 manifest 固定来源、许可、语言、case ID、split、内容 hash 和标签规则；模型辅助生成的数据必须人工核对，不能把模型输出直接当 gold。第一轮英文与当前本地基线一致；中文案例可作为独立分组补充，不混成未经验证的多语言结论。

gold 仅由 evaluator 读取，不放入 Handler / 模型输入；预期 source 使用稳定文档 ID 和证据片段，改变分块不重新定义 gold。索引语料在部署时可见，保留的是未用于调参的查询 / 标签；同一文档模板不能仅替换订单号后跨开发 / 测试集。公开仓库称“开发时未使用的保留测试集”，不称第三方盲测。

### 4.2 指标口径

| 指标 | 分母与失败处理 |
|---|---|
| RAG Recall@1/@3/@5 | 对全部可回答问题取平均；每题为检出的相关 source 数 / gold 相关 source 数。排名先按 source 去重；接口失败、无有效索引、超时记 0 |
| RAG MRR@5 | 全部可回答问题；第一个相关 source 名次的倒数，前五无命中记 0 |
| 无答案问题 | 当前 Search 总返回 top-k，先报告最高分和误检案例；没有拒答规则时不报告“拒答准确率”。如增加阈值，在开发集校准并冻结为新的检索策略 |
| 抽取字段准确率 | 正确字段 / 全部有效文档应抽取字段；任务失败、缺产物及缺字段均计错。金额按固定十进制精度、日期按固定规范比较 |
| 整单正确率 | 所有目标业务字段正确的文档数 / 全部有效文档；引文是否原文子串、是否支持目标字段另评，不拿存在引文代替字段正确 |
| 首次 / 最终结构合规率 | 两者均以全部有效文档样本为分母；首次指首attempt的首次模型调用，最终指任务最终输出。已执行但超时/无输出/非法JSON/截断计不合规，未执行单列incomplete且不计成功；另报以实际响应为分母的条件指标时明确命名 |
| 修正成功率 | 使用修正后满足结构 / 业务要求的样本数 / 进入修正的样本数；分母为 0 时标 N/A |
| 负例处理正确率 | 按事先定义的业务拒绝策略失败且未发布错误产物的负例数 / 全部负例；网络失败不能算正确拒绝 |
| 执行与费用 | 全部样本的终态、attempt、物理请求数、已知 tokens、费用未知次数、usage 覆盖率；首次 / 最终成功、排队 / 调用 / 整体耗时分开 |

source 级 top-k 与旧接口 chunk 级 top-k 区分命名。v2 评测在有界索引上实现 source 去重检索并测试排序规则；不将旧接口最多十个 chunk 的截断结果冒充完整 source 排名。

每个 manifest 样本必须有结果行，包括 rejected、dead、cancelled、timeout、预算未执行和后端不可用；没有执行的样本不能算通过。模型质量统计与任务正常结束分开。少量样本的 p95 附样本数，不宣称生产 SLA。

### 4.3 测量与改进

建议新增 evals/ 资源与标注目录、tools/evaluate_tasks.py、确定性 scorer 测试、docs/evaluation-report.md。runner 经安装后的 Python SDK 提交任务，通过产物 API 查询 / 检索，不绕过 JobForge 直接调用模型。runner 只枚举样本、限并发提交和汇总，不自行恢复或重试业务任务。

业务键采用有界的 run / variant / case / repeat 身份（必要时 hash 保持≤128字符）；提交幂等键独立。相同 case 的自动重投及人工 retry 保持业务键；新实验换 run ID，避免读缓存伪装成新推理。报告同时标记模型冷 / 热启动与 artifact.reused。

最多两条单因素实验：RAG 对比当前段落分块与保留标题上下文；抽取对比当前提示词与一版强化数字、日期及来源约束的提示词。每条实验固定模型、数据和其余参数；后端对比单列，不能同时换模型与算法后归因给算法。

先跑开发基线，再冻结主要质量指标、允许的非回归范围、调用 / 延迟预算和候选选择规则，最后在同一保留集运行baseline与已选candidate。S1b不提前运行或查看保留集推理结果。至少交付一次完整候选实验；正负结果都保留。没有证据改善则保留基线，不预先承诺提升百分比，也不通过反复查看保留集挑选方案。

## 5. 远程候选与费用控制

### 5.1 候选选择

建议首选候选为百炼同步 API：text-embedding-v4 与支持 JSON Schema 的 Flash 快照。调研时可用候选包括 qwen3.7-flash-2026-07-15；备用为保留当前模型 digest 的远程自托管 Ollama。具体供应商、地域、模型、可用性和预算仍待实施前确认，官方能力与限制见[调研记录](../research/ai-backend-evaluation-and-models-2026-09-16.md)。

百炼候选有两处显著差异：embedding 维度不含 384，单批最多十条；最多64块可能需要七个物理请求。v2 候选可先选1024维，建索引的物理 embedding 请求上限按实际分块计算并封顶为七；评测查询走独立调用预算。v1 的最多两次批量 embedding 与固定模型验收继续保留。新 profile 必须明确不同限额，并验证维度扩大后仍满足2 MiB产物上限。

继续使用同步 HTTP 与 Go context，关闭重定向和客户端隐式重试。单次逻辑模型操作（含embedding拆批）的总时间仍≤60s，并受attempt剩余deadline限制；各物理请求只能消耗剩余时间，不把七次请求各自扩成60s。只允许部署登记的 endpoint、模型、协议及参数，远程使用 HTTPS；密钥仅来自运行环境或 secret，payload 不控制出口。供应商工具调用、搜索和异步 Batch 不在首轮接入范围。

按供应商固定错误分类区分暂时限流 / 5xx / 网络失败与鉴权、参数、欠费、额度耗尽；不能把所有429都当可重试。队列仍是唯一自动重试调度者。若需尊重 Retry-After，S0 先决定如何映射既有退避；没有明确支持时不声称已经遵从，不在模型适配器内无界等待。

### 5.2 预算方案

费用上限用 B 表示，尚未取值。实施收费验收前冻结：供应商 / 地域、模型快照或可用版本、价格日期、样本数、变体数、重复轮次、并发、Token / 输出上限、物理调用上限和允许的故障重跑次数。没有 B 或凭据时只推进本地与确定性测试。

推荐正常评测 max_attempts=1，最多一次结构修正；先并发1的小批，再视预算提升。故障测试单独申请固定调用份额并明确 max_attempts，人工 retry 也计入同一验收批次预算。预算包含建索引、查询 embedding、修正、自动 / 人工重试，以及崩溃后可能重新发起的计算。

    估算费用 = Σ(输入 tokens × 对应输入单价 + 输出 tokens × 对应输出单价)

实际计算按价格表单位换算，并计入所选模型的其他收费项。优先使用供应商返回 usage；缺失或超时的调用记 unknown，不能按0元或0 Token结算。字符数不能直接当 Token 数，供应商估算工具 / tokenizer 的适用范围和误差也要记录。候选单价仅供预估，实施前重新核对，免费额度不作为已获得资源。

第一版需要区分两层控制：

- **请求额度硬限制**：业务侧调用额度在发请求前原子预留，按验收批次跨 Worker / job / 人工 retry 共享；含同步检索 API。新增业务表记录预留、已知用量或 unknown，不进入 jobs 状态机。同一预留不能再次用于发送，重投的新调用须重新预留；无响应、kill 后额度保守消耗，不盲目退款。数据库不可用时不发新收费请求；额度不足返回不可重试的业务错误。原文、密钥不入额度表。
- **货币费用估算**：预估费用与实测 usage 对账、达到预留阈值停止新调用；无法获取真实消费的进行中请求单列。供应商账户硬配额若可用则作为辅助。未验证供应商计费及所有请求边界前，不宣称“绝对不超 B”。

该小型额度表只为本轮真实远程验收与故障恢复提供边界，不扩展为多租户计费平台。若 S0 决定裁掉持久额度预留，只能保留单次运行的软预算，并从验收声明中删除跨进程硬调用上限，不能以进程内计数替代。

取消验证停止本地等待、后续调用和未提交处理；已发出的供应商请求可能继续计算 / 计费。成功产物复用只能防止重复发布，不能证明模型只调用一次。

| S5：可选备份恢复 | 主线交付后 | 隔离新库恢复与SDK/产物核对 | 限定环境恢复成立；不扩成生产HA/长周期留存验收 |

S1b 与 S2 可在 S1a 后独立推进；S3 的本地实验不等待供应商。S4 的历史证据整理 / W4 调查可独立进行。每个 PR 单独评审和记录实际检查，不把有凭据依赖的全部工作压成一个大 PR。

## 9. 当前版本证据与历史边界

S4报告分三层：存储微基准；真实SDK→HTTP→Gateway→Worker的固定耗时任务；实际AI任务。整体时间以SDK开始提交到观察到终态为准，注明轮询间隔；DB排队、Worker执行、模型调用与产物发布分别测量。小样本只报告对应范围，不借用历史no-op数据说明模型吞吐。

W4调查先确认真实领取数量、数据清理、schema与版本可比性，固定轮次和并发；必要时用执行计划、数据库等待与pprof解释差异。没有可比环境则形成“不可直接比较”的有证据结论；若重建基线须另经显式决策，不删除原失败。

演示复用 [demo-script.md](../demo-script.md)，增加PID、Kill/Wait、旧/新attempt/token、产物发布时间和自然lease到期的时间线。预热/模型下载不计入三分钟展示，另写干净环境启动步骤。模型可能重复调用与业务只发布一次分别讲清。

| 边界 | 当前状态 | 本阶段可以关闭什么 |
|---|---|---|
| 远程模型 | 仅本地真实验收；远程未验收 | 所选供应商/地域/模型与指定样本、预算、错误范围；其他供应商及取消退款不自动获得承诺 |
| 生产留存 | 开发观测栈与命名卷；生产留存未验收 | 可选限定环境备份恢复；HA/PITR、长周期留存、容量与真实RPO/RTO继续未验收 |
| 历史W4 | Claim 4.171→5.900ms/op，历史门禁失败 | 当前版本可比结果或有证据的重建基线决定；单次新基准不能自动关闭 |
