# JobForge 对外展示与接入体验优化方案

> 已完成方案：2026-10-16 经 PR #64、#68 交付，并发布 Preview。实施与验证见[交付记录](../../evidence/public-readiness-2026-10-16.md)；正文保留批准时的工作范围和完成标准。

日期：2026-10-16。版本：v1。状态：维护者已批准；交付入口与验证见[实施记录](../../evidence/public-readiness-2026-10-16.md)。

实施基准为已合并的 [PR #63](https://github.com/XJfyrh/JobForge/pull/63)，合并提交 `fe6dd385c4f1592b4f174b5372972c69b15fcd80`。本方案覆盖项目展示、首次 Run 接入、部署判断和外部贡献入口。

## 1. 目标与范围

让首次访问者能够回答四个问题：JobForge 替客服完成什么、实际结果是什么、如何开始使用、适合在什么条件下部署。

本轮交付直接通过 GitHub 仓库、Markdown、截图、公开视频和 Preview Release 呈现。**文档站、站内搜索本轮不做**，后续按需要单独评估。当前指南继续单源维护，历史 PRD、ADR、机器报告和原始证据保留原路径及正文。

本轮新增模型调用预算为 **0 元**。新版 UI 录像使用已有真实结果回看与明确标注的演示数据；真实故障证据复用既有原件。完整重跑真实模型或业务写入不属于本方案的免费录制路径。

## 2. 现状与关键判断

| 范围 | 已核实的问题 | 方案处理 |
|---|---|---|
| 项目入口 | README 有技术定位，但业务价值、可视结果和英文入口不足 | 首屏先说明业务价值，连接截图、视频、边界与工程证据 |
| 许可 | 根 LICENSE 和 README 为 Apache-2.0，SDK 元数据仍为 Proprietary；Agent 包未声明许可 | 发布前统一源声明及实际构建产物 |
| 业务说明 | 能力、人工审批、升级人工和动作边界分散 | 一页说明职责、人工介入条件和实际效果含义 |
| 工程展示 | 有架构文字、ADR及真实证据，缺少工程亮点页和架构图 | 用四个具体难题连接设计、代码和验证 |
| 演示 | 已有真实录像，但只指向本机目录；UI 已更新 | 新录工作台展示，保留历史真实故障片段及版本标识，提供公开播放入口 |
| 首次接入 | 默认 Compose 只启动零 profile、零预算的空控制面 | 增加免费、隔离的 v3 Run 体验，空列表查询只作为连通检查 |
| API示例 | OpenAPI 无 servers/examples；独立 Python 示例偏旧 Job 路径 | 增加 v3 SDK脚本、请求示例及完整配置入口 |
| 部署判断 | 端口、资源、期限和运维限制分散 | 集中部署参考，明确当前 v3 的已验证范围与生产缺口 |
| 外部贡献 | 分支规范包含个人前缀；有入门标签但没有对应 Issue | 公共规范使用通用命名，补首次贡献路径与具体小任务 |
| 文档理解 | 当前指南与大量契约、证据混合，缺集中术语表 | 调整现有导航，增加术语表与平台入口，不建设站点 |

三个表述需要保持准确：SDK README 已有 v3 代码片段；OpenAPI 缺少 servers 并不违反规范；旧 Job 路径已有特定 SLO，不能全仓统一改称没有 SLO。

## 3. 交付工作包

### A. 许可与发布元数据

优先级 P0，工作量 S，首个 Preview Release 的前置项。

- SDK 与 Agent 包统一声明 `Apache-2.0`，采用构建后端支持的 SPDX 元数据格式。
- 根 LICENSE 作为许可正文来源，构建时将其纳入各包的 wheel、sdist，避免独立手写多份正文。
- 保留新版 UI 中 Noto 字体和 Phosphor 图标的独立许可声明，并检查分发产物中的保留情况。
- 对齐 SDK描述、项目URL和仓库入口，突出当前 Run API，同时保留旧 Job API 的支持范围。

包内容或镜像变化使用新的构建摘要及匹配登记，历史冻结回执保持原样；公开质量数字继续标明原冻结候选版本。

验收：实际构建两个 Python 包，检查元数据、许可证文件及源码包内容；不以 TOML 文本检查替代产物检查。本轮发布入口为 GitHub Release，PyPI 上传另行安排。

### B. 首页、业务说明与工程亮点

优先级 P1，工作量 M。拟调整根 README，新增业务说明、英文摘要和工程亮点说明，并扩充现有架构页。

拟交付路径：`README.md`、`README.en.md`、`docs/support-overview.md`、`docs/engineering.md`、`docs/architecture.md`及配套图源。

首页价值主张采用：

> 把工单、订单、物流与政策证据整理成可审阅的售后方案，经人工批准后记录到工单。

首屏依次呈现价值主张、新工作台截图、演示入口、可核验结果和最短启动入口。技术定位作为下一层说明，使用“Go/PostgreSQL 管理执行、恢复、审批与费用，Python 执行受控 Agent 步骤”。

业务说明页必须区分以下内容：

| 主题 | 必须说明的内容 |
|---|---|
| Agent 完成什么 | 读取授权工单、订单、物流和政策，核对事实并提出有引用的处理方案 |
| 何时升级人工 | 已成立的结构化冲突、有效签收争议、当前丢失/损坏/退回异常，以及未交付且超承诺至少48小时；注明对应政策版本 |
| 何时补充信息 | 缺失必要关联、事件或问题描述；证据不足与事实冲突分别处理 |
| 谁能批准 | 所有业务写入需要独立人工审批身份，批准绑定原方案 |
| 批准后发生什么 | 保存结论、补充信息要求或人工跟进标记；实际效果通过独立回执确认 |
| 当前外部边界 | 人工跟进标记没有连接外部派单系统；不自动关闭工单、发送客户消息、退款或付款 |

用一个完整案例展示“问题、证据、方案、批准影响、实际回执”。“方案已批准”“工单已更新”“客户问题已解决”不能混用。

工程亮点聚焦四项，每项给出问题、实现选择和代码/验证入口：

1. PostgreSQL中的执行身份、租约与 fencing，以及进程中断后的步骤恢复。
2. 原方案绑定、独立批准、受控业务写入与幂等回执。
3. 调用前预留、累计预算和 unknown/hold 的处理。
4. 冻结候选、未见正式集、Fixed 对照与残余错答的可复核评测。

架构页增加组件图，展示 UI、Go 控制面/Worker、Python、控制库、业务库和模型服务，标出执行权、读写和凭据边界；增加一张业务提交后丢失响应、恢复读取回执的时序图。图保留可编辑源文件，并导出适合 README 阅读的版本。

英文入口先覆盖项目摘要、截图/演示、业务边界、结果与启动链接。现阶段不全量翻译历史材料。

首页数字使用固定版本结果：V9未见正式20案，Agent正确及完整证据各18/20，Fixed各11/20，配对胜8/平11/负1。标明日期、分母和报告链接；保留两案失败，不将小样本写成生产准确率，也不从恢复对照推导节费结论。

验收：首次访问者无需查阅阶段报告即可理解业务用途、动作范围和实际结果；每个公开数字及工程亮点均可进入对应证据。

### C. 首次 v3 Run 与 API接入

优先级 P1，工作量 M，是本轮主要技术不确定项。

拟交付路径：`docs/quickstart.md`、独立的`deploy/demo/`配置，以及`examples/run_submit.py`、`examples/run_review.py`、`examples/run_effect.py`和HTTP请求合集。配置字段参考并入下文部署参考。

先验证既有 integration target 能否组成免费、隔离的完整体验：通过公开 `/v2/runs` 创建真实 Run，经过 Go、真实 PostgreSQL和固定执行器协议，得到已保存方案及可查询结果。推理响应使用独立演示镜像中的确定性响应，界面和输出标注模拟范围，生产 registry 与模型端点边界继续保持原合同。

最小验收终点为 `awaiting_approval`，或明确无需动作的完成结果。空控制面启动和查询空列表不计作 hello run。免费机制体验证明接入与执行链路，真实模型质量继续引用原验收报告。

交付包括：

- 一篇从前置条件到可见结果的 Quickstart，包含启动、提交、查询、失败排查和专用环境停止命令。
- 配套演示配置与初始化入口，使用独立项目、明确端口和新建数据卷，输出实际Run ID及访问地址。
- v3独立脚本：提交并有界等待、读取方案/来源、人工审阅后批准或拒绝、查询效果与核对回执。
- curl请求合集和PowerShell对应方式，覆盖身份、提交、查询、审批、效果，以及401/403/409/410和未确认结果。
- OpenAPI补充本地/部署连接说明及请求、响应示例，复用可校验fixture；不写入秘密或假定存在的公共服务地址。

配置入口按基础控制、业务执行、审批和观测分组。变量注明所属进程、必填条件、缺省值及秘密属性；客户端示例统一命名，运行时既有配置名保持兼容。Quickstart使用一套完整配置，不要求读者跨多篇文档拼接必需变量。

“5分钟”作为依赖与镜像已准备后的体验目标，在Linux和Windows Docker Desktop上测量后决定公开文案。首次下载、构建及完整冷启动时间另行记录。若现有 integration target 无法复用，先明确最小实现差异和工作量，再确定该入口的完成范围。

验收：干净、独占的演示环境内得到真实Run ID、方案和结果，SDK、API和新版UI看到同一Run；没有真实模型调用或生产凭据。SDK每个方法的一次HTTP语义保持，等待循环由示例显式实现并受总时间约束。

### D. 部署参考与术语表

优先级 P1，工作量 S。部署参考从README直接进入，首先呈现当前v3适用性矩阵。

拟交付路径：`docs/deployment.md`、`docs/glossary.md`；现有运行指南链接到统一字段、端口和窗口说明。

| 场景或要求 | 当前范围 | 部署者需要补充的内容 |
|---|---|---|
| 本地开发、隔离演示 | 有实现与验证；默认不执行收费模型 | 依赖准备及隔离配置 |
| 有限预算、人工监督的业务评测 | 有真实验收证据 | 具体环境的策略、角色及预算登记 |
| Worker中断后的Run恢复 | 已验证特定进程故障路径 | 保持控制库与必要业务依赖可用 |
| 停写双库备份、新库恢复 | 已完成限定演练，恢复后默认关闭执行 | 停写窗口、备份空间及复核流程 |
| 在线跨库一致备份、PITR、数据库HA | 当前v3交付未覆盖 | 独立设计与验收 |
| 生产容量、长期Trace、外部告警闭环 | 尚未完成对应验收 | 真实负载、保留策略与告警演练 |
| 生产可用率、端到端延迟、RPO/RTO | 尚未建立当前v3目标 | 明确部署拓扑、测量口径与恢复目标 |

同页集中组件端口、网络暴露、数据卷、资源基线与时间窗口。资源说明先记录实际验证环境和峰值，尚未测量的最低配置标明未建立基线。窗口分别说明lease/heartbeat/attempt、Run与批次截止、审批、内容留存及晚到计量，不将某次manifest窗口写成通用产品常量。

当前v3服务等级声明采用以下范围：

> 当前 Agent v3 尚未建立面向生产部署的可用率、端到端延迟及灾备恢复目标。已有指标与有限环境测量供部署评估使用；旧 Job 路径的既有合同继续有效。

通用操作共用正文，Bash和PowerShell按平台并列。平台表区分Linux容器、Windows Docker Desktop、原生Windows Worker及尚未验收的平台。历史证据中的平台描述保持原样。

术语表覆盖Run、attempt、profile、held、unknown、ACK、gold、fence、receipt和sweep，提供中文含义、关联API/字段及操作影响。unknown按调用、计量和业务效果分别解释；ACK说明确认的持久事实；held与供应商已结算费用区分。

验收：外部SRE从一页内能判断适用场景、依赖、恢复边界和待补的生产能力；SDK或运维文档首次出现关键术语时可进入集中解释。

### E. 外部贡献入口与近期路线图

优先级 P1，工作量 S。

拟交付路径：`CONTRIBUTING.md`、`ROADMAP.md`及GitHub入门Issue。

- CONTRIBUTING使用通用分支命名 `<type>/<short-description>`，说明fork、分支、局部检查与PR流程；维护者个人前缀保留为个人工作方式。
- 增加首次文档贡献路径：选具体Issue、修改一处当前说明、运行 `python -m tools.ci_docs`、提交PR。前置条件列明Git和Python，环境安装时间与“15分钟完成一次修改”的目标分别计时。
- 整理3个小范围的 `good first issue`，分别面向术语链接、配置说明和API示例；每项附目标、相关文件与验收命令。费用、租约、审批核心不列为入门任务。
- 新增当前ROADMAP，仅维护近期、后续和暂不纳入的范围，链接到具体Issue；历史路线图继续保留历史身份。HA/PITR等能力不能仅因进入路线图就写成已有承诺。

验收：首次文档贡献不需要Docker、数据库或模型环境；公共规范不要求个人命名空间；入门标签有实际可领取任务。

### F. 新版演示与 Preview Release

优先级 P1，工作量 M；公开视频为本轮的公开演示入口。

新版视频以合并后的工作台为视觉基准，交付MP4、封面、中英文字幕、来源说明与SHA-256。原三分钟录像及其收据继续保留，新成片使用新文件和版本。

| 片段 | 目标内容 | 素材要求 |
|---|---|---|
| 0–20秒 | 客服问题、项目价值和最终结果 | 新版工作台或清晰结果画面 |
| 20–80秒 | 任务、方案、订单/物流/政策依据 | 已有真实结果的只读回看 |
| 80–125秒 | 审批影响、批准与实际更新的区别 | 新版交互若使用演示数据须标注；不能在原关闭批次上重做审批 |
| 125–160秒 | 业务提交后丢响应、恢复读取唯一回执 | 原真实故障片段，标明历史版本和实际耗时 |
| 160–180秒 | 验收数字、业务边界和接入入口 | 链接原报告及新的Quickstart |

主片保持业务叙事，原始JSON、调用账本与详细Trace通过工程页和独立证据片段承接。完整原始视频、实际耗时及剪辑来源可追溯。

首个GitHub Preview Release固定已验证提交和tag，附可公开的演示、字幕、复现入口、发布说明和校验值。版本号与SDK实际版本策略一致，不从PRD编号推导。先在仓库内完成可审阅发布材料，再执行公开发布。

README增加CI、License、Release三个信号，CI指向main实际检查；验收结果使用有日期和分母的数字卡片。同步仓库About、Topics与演示入口。公开附件使用白名单，排查token、DSN、签名密钥、原始敏感正文和本机私有路径；不把整个证据目录打包发布。

验收：访客无需登录即可观看视频、阅读边界、查看固定版本结果并进入复现说明；新UI展示、模拟交互与历史真实故障片段有清楚的来源区分。

## 4. 实施顺序与检查

| 顺序 | 交付单元 | 前置与退出条件 |
|---|---|---|
| 1 | A许可修复；C演示入口可行性核对 | 先构建核验许可；确认免费完整Run的最小路径与工作量 |
| 2 | B公开说明、D部署参考与术语 | 统一价值、动作和运维边界，确定录像脚本所用文案 |
| 3 | C Quickstart、配置与API/SDK示例 | 实际跑通免费Run，记录两种平台耗时和冷启动条件 |
| 4 | E贡献入口与路线图 | 以已稳定文档和检查入口整理真实小任务 |
| 5 | F录像、附件与Preview Release | 对前述最终版本录制、核对来源，所选CI通过后发布 |

S表示以现有能力和文本整理为主，M表示涉及运行入口、跨组件验证或媒体制作。演示复用核对是最早技术反馈点，其结果用于修正C的实现范围与排期。

按独立能力拆分PR，每个PR一次聚焦主审，修复后复核原问题及新增差异。验证按实际改动选择：文档检查本地链接、锚点及Linux大小写；包装检查实际产物；API示例检查schema与真实HTTP行为；演示涉及状态、事务或并发时使用真实PostgreSQL及相应race/固定Linux检查。最新head的CI required通过后合并。

本方案交付时只新增方案文件。启动实施后，从当时最新main创建短分支，保持历史schema、manifest、gold和证据字节不变。

## 5. 完成标准

1. 根许可、Python包元数据和分发产物一致。
2. README能直接进入新版截图、公开视频、业务边界、工程亮点、English和Quickstart。
3. 免费体验实际创建并展示一个v3 Run，模拟范围、前置条件和耗时明确。
4. SDK与HTTP调用者能从单个接入入口获取完整必需配置及可运行示例。
5. 部署者能从一页判断当前v3适用范围、平台、端口、资源与恢复边界；SLO声明不覆盖或撤销旧Job合同。
6. 外部贡献者有通用分支规范、可领取的小任务、术语表和局部验证入口。
7. Preview Release绑定已验证提交，公开视频和附件可匿名访问，原真实证据及历史失败完整保留。
