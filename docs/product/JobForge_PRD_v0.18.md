# JobForge PRD v0.18：S4 审批、受控写入与回执恢复

- 日期：2026-10-05（Asia/Shanghai）；状态：**Accepted；实现与验收见[当前状态](../status.md)**。
- 起点：`main@2a0fee2474df1aedbb8f118efb9dbe1efbd16fff`（文档治理 PR #59；S3 为 PR #58）。
- 技术决策：[ADR-0026](../adr/0026-approval-actions-and-receipt-recovery.md)。
- 适用范围：细化 [v0.7 §3/5/7/8](JobForge_PRD_v0.7.md) 尚未实现的审批与写入合同，扩展 [v0.17](JobForge_PRD_v0.17.md) 的原 Run 恢复至动作阶段。旧 profile 和历史待审批方案不获得写权限；其余既有合同继续有效。

## 产品增量

用户通过 HTTP/安装后的 Python SDK 查看不可变方案、批准或拒绝。批准后，现有 Go Worker 在同一 Run 的有效执行权下执行唯一登记动作 `apply_ticket_resolution`，并保存业务回执；拒绝正常完成为 `succeeded/outcome=rejected`。

写入仅记录方案结论，或将工单标记为待补充、升级人工跟进。不会自动关闭工单，不接真实客户、付款、退款或邮件。模型继续只有三个只读工具；人工批准不由模型决定，Python 不获得写入能力。S5 页面、保留集、实际清理/备份及长期运维演练另行交付。

## 行为合同

1. 新不可变 S4 profile 显式声明审批写入政策，沿用 S3 的有限恢复政策、现有模型策略、工具和预算。schema 1–3 的查询与原保守语义继续有效；升级部署不能批准旧方案后执行写入。
2. 受信鉴权配置提供稳定 `actor_id` 和独立 `approver` 权限。`operator` 保留提交/取消/retry 权限，不自动获得批准权；本租户无审批角色为 `FORBIDDEN`，跨租户为 `NOT_FOUND`。任何重放先检查当前权限，密钥轮换不改变审批者身份。
3. 决策绑定原方案 hash，只有批准/拒绝，不在线修改。审批决定与 `ready`/持久下一动作步骤同事务，正常继续不增加 `recovery_count`。鉴权后先识别已接受幂等操作，新请求才检查状态、方案与期限；同键异内容 `CONFLICT`，改变既有决定为 `APPROVAL_CONFLICT`。重放原决定不重复排队或改变批准者。
4. 许可仍为 `min(方案提交时间+1h, Run deadline)`，批准、排队、自动恢复和人工 retry 不延长。首次派发由控制面与取消锁同一 Run，固定业务请求、operation ID、精确内容、批准引用和全部依赖版本。一次业务请求最多一个已授权操作。
5. 业务接收端先在租户内识别 operation：同内容已应用返回首次回执，异内容 `ACTION_CONFLICT`；只有首次写入才核验受信签名、身份、期限、对象关系和完整当前版本。工单修改与回执在一个业务事务中提交。缺失订单/物流后来出现、物流新增事件、政策变化及索引绑定均参与校验；网络不在控制或业务数据库事务内。
6. 原 Run 的正常非终态恢复先查原回执。已应用则完成；无回执时仅可在原许可内、原 ID/原内容重发。已提交模型步骤不重跑，不重置三层预算或恢复上限。陈旧 Worker 的回执不能推进新的 owner/token/游标。
7. 已批准动作阶段的查询先于 profile 当前可用性、费用冻结/余额检查；这些条件仍可阻止新写入。许可过期只查既有回执，无回执以 `ACTION_AUTHORIZATION_EXPIRED` 结束并保留不确定效果，不能把无回执当作未写入。
8. 取消先于授权则不能派发。授权先于取消时在途写入可能完成，取消不撤销效果。终态后的有界 reconcile 只查既有 operation，至多10s、每请求最多一次业务查询、按租户限频，只更新独立效果视图，不重开 Run、不改变首次结果、不重发写入。无回执为 `unknown`。
9. 人工 retry 保持单链、新 Run、原业务请求/操作/费用批次及原7日窗口。先查原回执，再检查新模型/profile/capture 条件：已应用直接复用；已有授权且查不到回执则新 Run 以 `ACTION_OUTCOME_UNKNOWN` 结束，不重发、续签或规划新动作；依赖不可用不冒充“无回执”。首次授权前失败才可按原规则捕获新快照、重新核查。
10. Run 状态、首次结果与效果分开。查询明确区分 `none/proposal/approved/applied/rejected/unknown`，`none` 表示尚无已接受结果，兼容原 `no_action`（仅已提交的明确无需动作）；`approved` 只是许可，`applied` 只表示记录/标记已提交，均不表示客户问题已解决。取消后发现 applied 只补效果视图。既有模型 `unknown/full hold/frozen` 原样保留，查询不增加模型调用或伪造费用结算。

源契约新增 approval/effect/reconcile 与动作/回执字段，具体请求、错误、角色及内部 RPC 见 ADR-0026。原错误 envelope 和失败 Run 查询 HTTP 200 保持。

## 真实执行与交付门禁

真实执行使用独立验收 manifest，明确有限累计费用、有效窗口、Run 上限、样本、故障边界、批准规则及审查放行记录。收费前完成免费检查和独立源码/测试审查；执行后验收通过才允许合并。不自动补样到通过、不充值、不动 gold/旧证据或旧冻结批次。具体运行额度与审查过程属于该批次验收记录。

调用前核对当天官方模型/价格和账号只读状态，建立独立控制/业务库、新不可变 profile/batch，使用真实 DeepSeek、MiniLM/pgvector、业务 HTTP/PG、正式 Go/Python 进程及安装 SDK。验收操作者的批准规则在首次调用前冻结：仅当待审批原始输出的协议、来源、原冻结业务谓词均通过，安全审计无违规且可验证，动作/目标状态在既有允许集合内时批准；拒绝场景按manifest拒绝同样可审批的方案。评分器/gold留在验收侧，生产不读答案，不人工编辑回填方案。模型业务失败保留，因未获批准而未进入动作路径的项不能算动作通过。测试自动化审批明确归属验收操作者，模型没有审批身份。

最终提供简洁 S4 报告、机器摘要和外部原始证据引用，分列机制、模型质量、失败原因、调用及 known/held 费用。observed usage 按冻结费率计算，不称已结算账单；尚未审查/执行的阶段继续标为未通过。
