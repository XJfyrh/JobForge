# JobForge PRD v0.9：S1-B Run 执行身份与调用账本

- 日期：2026-09-16；状态：提案，待独立审查和合并；本文件不代表实现通过。
- 基线：[PRD v0.7](JobForge_PRD_v0.7.md)、[v0.8](JobForge_PRD_v0.8.md)。本增量细化 S1-B，不改变 S2～S5 的退出条件。
- 决策：[ADR-0017](../adr/0017-run-admission-and-call-ledger.md)。S1-A 已经 [PR #38](https://github.com/XJfyrh/JobForge/pull/38) 合并，不能代替本切片验收。

## 1. 用户可观察行为

通过 Python SDK 提交工单，获得唯一 Run；按租户查询状态、步骤、事件和方案。重复提交返回首次 Run，取消禁止后续步骤与调用授权，人工 retry 创建新 Run 并继承业务身份及共享额度。Worker 的执行权和每次可能发出的请求都先在 PostgreSQL 中取得授权。

S1-B 提供这些能力的生产存储、服务、HTTP/Worker 源协议和 SDK，使用真实 PostgreSQL、HTTP 与确定性故障服务验证。正式受监管 Python 执行器、DeepSeek profile、40 例固定流程及真实费用证据在 S1-C 完成。B 的测试服务不作为生产模型注册；缺少可用 profile 时拒绝提交，不展示假业务成功。

## 2. 本次细化

1. 区分业务请求、Run、attempt、逻辑工具执行和物理 HTTP 调用五种身份。只有 Run 可以领取；其余记录不独立调度。
2. 业务请求的所有人工 retry 共享根 Run 的预算账户。12 次 chat、8 次工具、8 次 query embedding 和一次协议纠正是整个家族的上限，因此每个 Run 也满足 v0.7 的上限。新 Run 不恢复额度；新业务意图须新业务请求键，仍受 tenant 和批次总额度限制。
3. 提交先取得幂等业务快照，再用短控制库事务创建 ready Run。没有跨库原子提交、initializing 状态或补偿调度器；未被 Run 引用的快照可能保留，须明确容量和清理边界。
4. 业务 metadata 增补受信完整版本向量，覆盖缺失关系、订单、物流聚合、政策和索引；不是由模型声明版本。
5. 免费 HTTP 也需要调用授权。一次 search_policy 的版本查询、模型身份查询、embedding 和业务检索分别记账；逻辑工具上限不等于物理请求上限。
6. 调用状态和业务状态分离。完整合法 usage 可在输出校验失败时结算，也可在 lease/Run 结束后补齐；它不能提交旧步骤或改写 Run 终态。缺少 usage 的可能调用保留全额占用。

## 3. 需求—验收映射

| ID | 要求 | 实际验收证据 |
|---|---|---|
| B-01 | API/SDK 严格请求、鉴权和提交幂等 | 真 HTTP+PG+已安装 SDK；两租户、异内容冲突、同业务键不同提交键、并发retry仅一个后继、隐藏重试为零、分页和错误映射 |
| B-02 | 可信快照与接纳事务 | 完整版本向量及缺失关系；并发同键、业务 capture 成功后控制提交失败、重发复用、retry 新快照、无跨库长事务 |
| B-03 | Run 原子 Claim 与有界容量 | 双 Worker 竞争、到期尚未重领、session/token 错误、锁等待跨 deadline、容量计数一致，真实 PG/race |
| B-04 | 取消、停止和恢复预算 | cancel/提交/预留竞争；stopping 不续租；停止确认与 lease 到期；后到 cancel/总期限优先；恢复最多三次，重复关闭不重复计数 |
| B-05 | 顺序步骤与首次结果 | 当前执行权下重复 ACK、异内容冲突、陈旧写入拒绝、下一游标由服务端决定、checkpoint 总上限、yield 丢 ACK 只读确认 |
| B-06 | 方案与效果分开 | 原子提交方案、完整审批绑定、关闭 attempt 与释放容量；无动作才 succeeded/no_action；等待期限收敛，S4 前无批准/写入接口 |
| B-07 | 三层预算原子预留 | 两 Run 争抢最后额度、三层全成或全败、整数边界、人工 retry 不重置、查询 checkpoint 不受剩余额度阻断 |
| B-08 | 每次派发身份 | 一次命令重复不新增发送；预留 ACK 丢失、发送前后断连、unknown 占额；新发送新 ID；search_policy 每一步在取消先提交时拒绝新许可；已授权在途窗口单独披露 |
| B-09 | usage 与运行状态隔离 | 首次结算/重复/冲突；输出不合法但合法 usage；终态后计量不推进状态；30日补报窗口与无级联返还；超出保守上界冻结新派发并保留异常 |
| B-10 | 源协议与工程复现 | OpenAPI、Proto、执行器 JSON Schema/共同 fixture；生成一致性；Windows 真 PG、Go/race/lint、Python/SDK、SQLFluff、Buf；新 Claim/账本查询 EXPLAIN 和定向基线 |

这些用例映射 S1-03、05、07～10 和 V3-03、07～09 的基础能力。B-08 的确定性故障服务不证明真实模型取消/计费，B-04 的数据库恢复不代替 S3 的实际 Kill/Wait 和自然恢复验收。

## 4. 公开边界与资源约束

公开请求只选择已登记的 profile 和已授权的 budget_batch；不能设置 tenant、Worker、lease、费用单价、URL、API key、工具定义或任意代码。profile 的具体云端价格、最大输入和批次金额在 S1-C 开始收费前另行冻结，B 不引入可收费的默认配置。

提交默认 Run timeout 3600 秒，可选 1～86400 秒；自首次控制库接纳的数据库时间起算，重发不延长。业务快照 capture 单独最多 10 秒。attempt、lease、单调用、输出和 checkpoint 上限继续服从 v0.7；详细身份、计数及锁序见 ADR-0017。

终态与 checkpoint 保存 7 日、业务请求/操作身份至少 30 日；本切片不实现删除任务或自动释放 unknown。没有清理不代表已经通过生产长期留存。S5 的清理、备份恢复和身份防重窗口仍为必需验收。

## 5. 交付与完成口径

契约先经独立上下文审查和 PR 合并，随后实施。实现 PR 必须逐项报告 B-01～10 的通过、失败、跳过和未运行，给出本地命令及仓库外决定档案。仅全部满足才标记 S1-B 完成；S1-C 和整个 S1 仍分别判断。

历史远程模型与生产留存未验收、W4 性能门禁失败、AT-25 跳过继续保留。新 Run 的定向测量是自己的基线，不替代或冲销 W4 结论。
