# ADR-0022：S1 收尾新批次与累计费用授权

- 状态：**Accepted（随 [PR #53](https://github.com/XJfyrh/JobForge/pull/53) 独立审查通过并合并时生效）**；日期：2026-09-17。
- 决策者：维护者明确授权本次 S1 收尾范围及新增累计 5 CNY，独立 Agent 审查后按 PR 流程接受。
- 关联：[PRD v0.14](../product/JobForge_PRD_v0.14.md)、[ADR-0021](0021-first-cloud-batch-admission-and-launcher.md)；实现与真实验收另行记录。
- 部分取代：仅对本次 S1 收尾，取代 ADR-0021 §2.2、§4、§5.2、§6 中“首批停止后没有新批次授权”“仅原 5 CNY 批次”的适用范围，及 §4 的每批固定 5,000,000 microyuan 值；合并接受后适用下述累计上限与较小 batch 上限。ADR-0018/0020 的首批历史授权不改写，ADR-0021 其它决策继续有效。

## 1. 上下文

原首批已经停止，未闭合 40 案真实验收。其提示修复、实际进程停止竞态修复和诊断增量须完成工程门禁并绑定新部署；历史缺失日志不能补造，旧中断不因新修复而被追认根因。维护者明确要求修复后做新批次，授权本次所有新增验收费用累计不超过 5 CNY，并保留全部旧事实。

ADR-0021 有意未定义首批停止后的人工决定。因此以最小增量记录这项授权，不静默改写首批合同，也不新增预算服务或放宽持久停止谓词。本文合并接受前不能用作新批次实施依据；接受设计和实际完成收费前置、真实验收分别记录。

## 2. 新批次准入

1. **原批不可恢复。** 原 batch `a4ad1772-3af9-4985-8040-5e3ed6aba1a9`、Run、session、账本、hold、attempted/stopped 和原始证据保持原状；只读追加导出及已有原身份窄晚到确认继续按 ADR-0020。没有 reset/thaw、补假 Commit、改账或删除标记入口。
2. **先停止并核对。** 新批次前确认所有前批 launcher/driver/Worker 与旧受监管组的实际退出、Wait/组消失及无自动重启；保留容器退出事实和有界日志。原在途 RPC 可能在停止检测后提交，须读持久账本核对，不能把本地 stopped 当成退款、数据库未提交或 frozen 已确认。
3. **持久确认不能绕过。** 前批已预留 chat 的原 report、known/普通 observation 和步骤 Commit，或 ADR-0020 §8.1 的窄二次纠正终态失败屏障，必须有完整事实；缺失时不以新 batch 绕过。原非 chat unknown 保留原 token/金额 hold，按实际计费能力核算，不伪造 DeepSeek report 或零费用。必要确认不完整、仍在途或未知费用无法安全核算时不启动。
4. **身份与构建重新绑定。** 使用新 batch UUID/key、专属 Worker ID、新 profile ID/hash、新 tenant 账户及固定 40 行的新稳定业务/幂等键。重新核对修复后源码、prompt/schema、安装包和镜像 receipt，实际镜像与配置一致；旧 profile 不原地替换。保留已审查业务数据/政策/索引与冻结 scorer，生产镜像不含 gold。
5. **收费前置仍有效。** 先完成实际改动的相称验证、必要强制 CI 和独立审查，复核当时官方模型/价格与账号可用性；不新增收费探针。不具备前置条件则保持新 profile disabled。旧 profile 撤销未来执行能力不改变其历史定义或晚到权限。

## 3. 跨新批次的累计上限

本次授权标记为 `s1-closeout-2026-09-17`，只是部署记录中的人工授权引用，不新增数据库实体或执行权限。所有引用本授权的新批次共同使用 **5,000,000 microyuan**；原首批的费用单列，不能视为原批额度恢复，也不能把每个新批次计作新的 5 元。

新批次 i 的最高费用上限为：

```text
R_i = 5,000,000 − Σ known_cost_microyuan − Σ held_cost_microyuan
```

求和覆盖本次授权下所有已启动的前批共享 batch 账户，一条调用只计一次，不再叠加其 family/tenant 镜像计数。只有全部前批派发者已停止、必要持久确认完整后才取样；读取时间、每批 ID、known/held、原未知项及停止证据追加保存。只有已按原合同持久确认的结算才能释放相应 hold，observed usage 或余额差不能替代账本结算。

新 batch 的实际持久费用上限必须 `0 < limit <= R_i`，且余量足够下一调用的原保守预留；不足则停止收费。本次首个新批次可至多 5,000,000，后续批次扣除已知费用和未释放 hold。family、tenant 和固定 profile 的原上限保持 5,000,000，由共享 batch 的更小上限决定实际可预留额；不以多租户相加扩额。沿用原单次 hold、次数和 token 上限。

最低实现是复用现有批次额度字段、登记校验、只读 inspect 和仓库外追加部署记录；若后续批次需要降低上限，仅增补明确有界 batch cap 的准备/校验接缝及相称测试，不改 profile/价格合同，不提供增资或自动续跑。PG 仍是当前 batch 预留、known/held 与冻结的唯一事实源，部署记录只约束本次受信单维护者的跨批授权；它不是跨管理员并发安全的全局预算服务。

禁止同时运行或预先启用两个新批次。新批次启动前必须核对前批已不具备新派发能力；不能靠稍后记账、前批预检缓存或人工估算允许重叠。供应商真实费用仍依赖已核对计量合同，unknown/full hold 不等于账单或零费；无法确认上界时停发报告，不充值、不额外授权、不切换供应商。

## 4. 每批运行与验收保持

每批固定 6 小时，north/south 各 20 案共享 batch，Worker/tenant/profile 容量全为 1。唯一 launcher 监管一个 Worker 和一个 SDK driver，固定 `init=true`、`restart=no`、部署绑定状态目录和 attempted 排他屏障。每案最多一次 Submit；停止后只读 export，不重新 launch、Retry、换键续跑或自动新建批次。

全部原持久 chat guard、first-write-wins、unknown/full hold、frozen、原身份 late、ACK/Commit 与 Kill/Wait/EOF/Join/组消失屏障不变；本合同不能让不完整旧事实恢复执行权。若修复后新批仍停止，保留全部 40 行及失败/未尝试，按 §2～3 重新核对后才能在本授权余量内开展另一完整新批次。

C-01～C-08 / L-01～L-08 继续适用。单次完整新验收固定 40 案全部经正式链路执行且安全证据完整、硬失败为 0，才可结合既有 S1-A/B 证据闭合 S1；成功与明确业务失败分开，不能跨批挑选成功案例拼成 40 案。业务成绩分母始终 40，不新增正确率门槛、不改标签、不打开保留集。`awaiting_approval` 只是持久方案完成并释放 lease，本次无批准或业务写入。

## 5. 影响、替代方案与验证

公开 HTTP/SDK/gRPC/Proto、Run 状态、错误码、数据库 schema 和 migration 均无变更。继续 at-least-once、PostgreSQL 唯一事实源、租约与 fencing 合同。费用聚合与部署准入有人工记录成本，但不创建第二调度器或通用预算平台。

不采用恢复旧批/清空 hold（破坏历史与停止合同）、每批重新给 5 元（超过维护者累计授权）、仅看账号余额（不能证明在途和每调用事实）或新增全局预算平台（超出本次 S1 收尾）。不为文档增量重跑已有效的模型或全量测试；实际代码变更、失败和强制 CI 决定验证范围。

接受本合同前完成独立文档审查、链接/差异检查及必需 PR CI；正式新批启动前留下 §2～3 的只读核对与部署 receipt。实现若调整 batch cap，测试首批原值、较小 cap、非法/越界值以及重复 bootstrap 不重置；沿用已有持久账本和停止测试，不新增无关恢复/性能验收。

最终报告包含各新批及历史首批的完整结果、费用/hold、构建绑定和复现步骤；缺凭据、余额、供应商合同、模型资源或无法安全核算费用时停止收费并报告具体缺口。S1 闭合后停止，不推进 S2～S5；历史 W4 失败、AT-25 跳过与生产长期留存未验收继续保留。
