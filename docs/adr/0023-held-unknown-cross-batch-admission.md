# ADR-0023：保留未知费用预留后的独立新批准入

- 日期：2026-09-17；状态：Accepted（随本决策 PR 独立审查通过并合并时生效）。
- 依据：维护者要求重新评估过严的计量确认决策，以可用 S1 成果为目标；原新增累计 5 CNY 授权不变。
- 对应：[PRD v0.15](../product/JobForge_PRD_v0.15.md)。
- 部分取代：ADR-0022 §2.3、§3、§4 中把前批每个 chat 的 known/普通 observation/Commit 完整性作为所有后续独立批次前提的要求。ADR-0020 的原调用确认、当前批停发及不可覆盖账本合同不变；不放宽成功步骤提交。

## 问题与取舍

S1 收尾批 `901bce9d-9337-406d-9f90-f6427daf11aa` 的 DEV-015 请求已发出，HTTP 200 headers 后未取得完整响应，首份审计持久化为 unknown，full hold 为 2,105,344 microyuan；已知费用 48,653 microyuan。派发者已经退出，原 batch 冻结。无完整响应的历史调用不能凭空补出 known/普通观察/Commit。

原规则把“这次步骤能否成功”和“未来独立任务能否获得资金”绑定，导致有界失败永久阻止新验收。对不写业务的固定 S1 流程，成本上界已经全额占用时，要求旧失败调用变成完整成功确认对新任务没有额外预算保护。接受历史未知成本、保留其全部预留并减少新任务额度，更符合可用成果目标。

## 决策

允许受信维护者在原 5 CNY 累计授权内，记录一次有界人工准入，启动新的完整 40 案批次；不要求符合下列条件的历史 unknown 变成 known。不是自动续跑器、退款功能或旧批解冻入口。

必须同时满足：

1. 全部前批 launcher/Worker/driver 和受监管进程实际退出、Wait 完成、无自动重启；原 dispatch/call/lease 窗口已过，无可继续发送的进程或在途控制请求。读取最新持久账户和调用记录，不能只看 stopped 文件。
2. 原 unknown 是**未取得完整响应的传输/读取失败**；事前 Reserve、调用身份、固定目标/请求约束、首份 unknown report 以及完整 monetary/token hold 均可核对。根因未定位不伪称已修复；未知不能计零。
3. 上界依赖已核对的供应商模型/定价及固定请求合同；不存在已观测的身份/模式不兼容、measurement anomaly、报告冲突、超预留计数或价格合同失效。上述异常不能套用旧费率/hold 解锁新批；明确超界或上界无法成立时仍停发。
4. 所有旧 Run、report、observation、Commit、账本、冻结、attempted/stopped 及原始证据保留。缺失字段继续缺失；不重试原 call，不把余额差或人工估算写成结算。
5. 以各已启动 batch 账户一次聚合，计算 `R = 5,000,000 − Σknown − Σheld`；不叠加 tenant/family 镜像。新共享 batch 的**持久**费用上限 `0 < cap <= R`，且足够下一调用保守预留。新批独立身份、profile、配置/构建记录、新控制库的分栏不得重复计数或扩额；只运行一个批次。

本次已知状态的计算为 `5,000,000 − 48,653 − 2,105,344 = 2,846,003 microyuan`，启动前仍须重新取样。原 2026-09-16 首批 97,526 microyuan 费用单列，512 embedding token hold / 0 monetary hold 保留。若后续再失败，仅在同一累计上限和本节条件内评估；剩余额度不足即停止，不充值或提高授权。

## 最小实现

`agent-control prepare-support` 增加 `--batch-cost-microyuan`，省略时保持 5,000,000；显式输入仅接受 `1..5,000,000`。仅改变共享 batch 的 cost 上限；tenant/family/profile、40 行身份、次数/token、6h、单 Worker/单案例串行保持原合同。两份 control 配置及 launch 的配置摘要绑定该值，inspect 必须与实际 PG 一致。bootstrap 重放不能覆盖已有额度或消费。

实际调用仍经原 Go 租约/fencing、事前事务预留、report/普通观察 ACK、Commit 和 Wait/EOF/Join 屏障；预算不足时 PG 拒绝新预留。当前批未知仍按原规则冻结并退出，本决定只解除符合条件的历史失败对**独立新批**的永久禁止。批内自动隔离/重试、通用跨管理员预算服务及更小单调用预留不在本次实现。

为下次实际异常保留安全的固定错误类别、读取阶段及字节数诊断；不记录响应正文、请求头、凭据或任意异常文本，不改变请求、usage 解析、收费/停止语义。不能把新增诊断当作旧响应已经补齐。

## 验证与验收

- 准备器验证默认上限、较小上限、0/负数/超界/非法值、两份配置只改变启用集合、冻结摘要与不可覆盖输出。
- 真实 PG 验证较小 batch 上限约束不同租户共享预留，unknown hold 仍占额，重复 bootstrap 不重置/扩大额度；原确认与冻结测试继续有效。
- 诊断若改动，验证断流/限额/取消的固定类别和不泄露内容，真实 Linux HTTP 路径适用测试通过。
- 所有适用 CI 及独立审查通过后才收费。费用持久上界、停止证据、跨批汇总与实际部署 receipt 追加留存。

S1 的完整 40 案正式执行、安全证据完整、0 硬失败、业务/结构/来源/安全分层评分、安装 SDK 查询与复现要求不降低；不跨批拼接成功样本，不改 gold 或打开保留集。`awaiting_approval` 只是方案完成，不批准/写入。S2～S5 不启动。

## 未采用的方案

要求供应商补齐不可恢复的响应再继续，会把产品可用性绑到无法保证的历史凭据；释放 unknown hold 或按经验费用扣款会失去预算上界。直接解冻/重跑原批会破坏身份与执行历史；自动忽略所有 provider 异常会掩盖定价合同失效。降低每次输入预留需可信 tokenizer/输入上界证明，此时没有必要为完成 S1 引入该新依赖。
